# TripGo

Реализация 1 лабораторной работы «Разработка микросервисов на Go».

## Требования

- Go 1.27.1
- `tripgoctl`
- Docker для контейнерного запуска

## Локальный запуск

В корне репозитория выполните:

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make migrate
make run
```

`tripgoctl cluster start` выполняется единожды.
`tripgoctl environment start` создаёт локальный `.env` с адресом PostgreSQL, нужно дополнить недостающие поля из `.env.example`.
`Makefile` загружает `.env` для `make migrate` и `make run`.
`make test` запускает `go test -race ./...`.

`make migrate` применяет миграции до запуска сервиса. При запуске сервис проверяет соединение с PostgreSQL и не стартует, если база недоступна. HTTP-адрес задаётся `HTTP_ADDR`.

## Переменные окружения

`.env.example` содержит примеры значений. Рабочий `DATABASE_URL` берите из `.env`, созданного `tripgoctl`.

| Переменная | Пример | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `LOG_LEVEL` | `info` | Считывается конфигурацией; структурированные логи относятся к ЛР2 |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет остановки |
| `DATABASE_URL` | из `tripgoctl` | Подключение к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимальное число соединений пула |
| `DATABASE_MIN_CONNS` | `2` | Минимальное число соединений пула |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Максимальное время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Таймаут подключения и стартовой проверки БД |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Таймаут запросов к БД |
| `HTTP_READ_TIMEOUT` | `5s` | Таймаут чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | `2s` | Таймаут чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | `10s` | Таймаут записи ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Таймаут неактивного соединения |
| `IDEMPOTENCY_TTL` | `24h` | Срок действия ключа идемпотентности |
| `IDEMPOTENCY_CLEANUP_INTERVAL` | `1h` | Период очистки просроченных ключей |

Все переменные обязательны. Длительности задаются в формате Go (`s`, `m`, `h`) и должны быть положительными. Количество соединений проверяется при старте.

## HTTP API

| Метод и путь | Результат |
|---|---|
| `POST /api/v1/trips` | Создание поездки: `201` и `Location` |
| `GET /api/v1/trips/{tripId}` | Получение поездки: `200` |
| `POST /api/v1/trips/{tripId}/finish` | Завершение поездки: `200` |
| `GET /health` | `200`, без обращения к БД |
| `GET /ready` | Проверка БД: `200` или `503` |

Ошибки ручек поездок имеют `Content-Type: application/problem+json` и поле `code`: `invalid_request` (`400`), `trip_not_found` (`404`), `driver_busy`, `trip_completed`, `idempotency_conflict` (`409`), `internal_error` (`500`). `/health` и `/ready` возвращают JSON со статусом `ok` или `unavailable`.

Пример создания поездки при `HTTP_ADDR=:8080`:

```bash
curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c","driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5","start_point":{"latitude":59.9398,"longitude":30.3146},"end_point":{"latitude":59.9290,"longitude":30.3626},"price":1450}'
```

Ответ `201` содержит заголовок `Location` с путём созданной поездки. По этому пути можно выполнить `GET` или добавить к нему `/finish` для завершения поездки.

Для идемпотентного создания добавьте заголовок `Idempotency-Key` со значением UUID. Первый запрос возвращает `201`, повтор с тем же ключом и телом - `200` и ту же поездку, тот же ключ с другим телом - `409 idempotency_conflict`. Без заголовка действует обычное создание.

## Принятые решения

- **Транзакции.** Менеджер `Do` начинает транзакцию и помещает её в контекст. Репозитории работают через неё либо через пул, если вызваны вне `Do`. Вложенный `Do` использует уже открытую транзакцию. Если операция возвращает ошибку или паникует, транзакция откатывается; при успехе делает коммит. Создание поездки записывает строку в `trips` и начальный статус в `trip_status_history` атомарно. Если передан ключ идемпотентности, его запись входит в ту же транзакцию.

- **Уровень изоляции `READ COMMITTED`.** Выбран, потому что текущим операциям не нужен неизменный снимок данных на протяжении всей транзакции. Каждый SQL-запрос видит уже зафиксированные изменения. Более строгий уровень изоляции для этих операций не требуется.

- **Уникальный индекс.** Частичный индекс `trips_one_active_per_driver` запрещает две поездки со статусом `active` для одного водителя. При одновременных `INSERT` второй запрос ждёт результат первой транзакции: если она зафиксируется, он получит ошибку `23505`, которая превращается в `409 driver_busy`; если откатится, второй запрос сможет создать поездку.

- **Идемпотентность.** Клиентский UUID, SHA-256 тела, ID поездки и время истечения хранятся в `idempotency_keys`. Резервирование ключа выполняется в транзакции создания поездки. Просроченный ключ можно использовать повторно. Очистка запускается при старте и далее раз в `IDEMPOTENCY_CLEANUP_INTERVAL`. По умолчанию ключ действует 24 часа.

## Docker

Dockerfile собирает бинарный файл в Go-образе, затем переносит только его в `distroless`. Процесс запускается от непривилегированного пользователя. `.dockerignore` исключает `.git`, локальный `.env`, тестовые Go-файлы и служебные файлы окружения.

В Linux контейнер можно запустить с сетью хоста: так адрес PostgreSQL из `.env`, созданного `tripgoctl`, остаётся доступен.

```bash
tripgoctl environment start
make migrate
docker build -f deploy/Dockerfile -t lab1:latest .
docker run --rm --network host --env-file .env lab1:latest
```

После запуска можно проверить `/ready` на адресе из `HTTP_ADDR`. Размер локально собранного образа `lab1:latest` около 31,4 МБ.
